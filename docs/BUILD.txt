# 构建、烧录与环境复现

从个人仓库根目录执行 tools 下的脚本。应用工程入口已迁至 sdk/apps/esp_app，
官方 SDK 已完整纳入 sdk/esp-idf，不再依赖 ~/esp 或 E 盘上另一个 SDK 源码仓库。

## Linux / WSL

需要 Git、Python >= 3.9（含对应 venv）、Ninja 和官方依赖：

```bash
sudo apt-get update
sudo apt-get install git wget flex bison gperf python3 python3-pip python3-venv cmake ninja-build ccache libffi-dev libssl-dev dfu-util libusb-1.0-0
# Ubuntu 20.04 的默认 Python 3.8 不满足要求，需并行安装：
sudo apt-get install python3.9 python3.9-venv
cd /home/ax2869/esp32-speaker
bash sdk/tools/setup.sh
bash sdk/tools/build.sh
bash sdk/tools/build.sh menuconfig
bash sdk/tools/build.sh size
```

setup.sh 校验内置 SDK，安装 SDK 推荐的 CMake 3.30.2、ESP32 工具链及隔离 Python 环境。
Ubuntu 20.04 的系统 CMake 3.16 无法正确处理此 SDK 的蓝牙库路径，构建使用已安装的官方推荐版本。
工具默认 ~/.espressif，构建输出默认 <仓库>/build/linux。
首次安装需联网获取编译器与 Python 依赖，SDK 源码不再另外下载。
SDK 路径发生变化后先运行 setup.sh，让官方工具登记该路径对应的 esp32 目标。
BUILD_PATH 可覆盖构建目录，IDF_TOOLS_PATH 可覆盖工具目录；迁移构建目录后使用新的空目录。
SDK_PATH 可指定同一导入快照的副本；它仍必须通过整个快照校验。

## Windows

准备 Git、Python >= 3.9；在本地 Windows 检出目录运行：

```powershell
.\sdk\tools\setup.ps1
.\sdk\tools\build.ps1
.\sdk\tools\build.ps1 -Action menuconfig
.\sdk\tools\build.ps1 -Action size
```

工具默认使用 %USERPROFILE%\.espressif；优先使用环境变量 IDF_TOOLS_PATH。
自定义工具目录时，setup.ps1/build.ps1 传入相同的 -ToolsPath，例如：

```powershell
.\sdk\tools\setup.ps1 -ToolsPath "$env:USERPROFILE\.espressif"
.\sdk\tools\build.ps1 -ToolsPath "$env:USERPROFILE\.espressif"
```

构建输出默认 <仓库>\build\windows，可通过 -BuildPath 覆盖。
-SdkPath 可指定同一 SDK 快照副本。源码导入包含较深的第三方路径，克隆时可使用
`git -c core.longpaths=true clone <个人仓库地址>`，检出后在该仓库配置 core.longpaths=true。
建议 Windows 使用本地检出，WSL 使用 Linux 内部检出并通过 VS Code WSL 扩展开发。
若确实用 Windows 原生工具链编译 WSL 中的源码，必须用 -BuildPath 指定 Windows 本地输出目录；
仅 pushd 映射盘符不够，Python 会将路径还原为 UNC，而 CMD/Ninja 不支持 UNC 作为当前目录。

## 配置与接口

产品目录：sdk/apps/esp_app/board/ESP32/board_esp32_speaker。
引脚、LCD 开关与参数、蓝牙名称、初始音量统一在 board_esp_proj_cfg.h 修改；产品 Kconfig.projbuild 已移除。menuconfig 仅用于 ESP-IDF 系统配置，分区表在 partitions.csv。
已有 sdkconfig 中的旧 CONFIG_SPEAKER_* 项不再控制产品行为；迁移后执行一次 reconfigure，再正常编译。
sdkconfig.defaults 只提供首次默认值；已有配置 sdk/apps/esp_app/sdkconfig 优先。
分区表路径为相对应用工程的 board/ESP32/board_esp32_speaker/partitions.csv。
工具与构建缓存不可跨平台混用；不要让两个平台同时改写同一份 sdkconfig。

SDK 校验和轻量检查：

```bash
python3 sdk/tools/check_sdk.py
python3 sdk/tools/test_sdk_snapshot.py
```

安装入口和手动 check_sdk.py 覆盖所有导入文件的 SHA256，包括递归依赖中的预编译库；修改或缺失时校验终止。
日常构建仅核对锁定版本与快照来源信息，避免在 WSL 共享路径重复扫描全部 SDK；需要检查 SDK 文件完整性时运行上述完整校验。
不需要、也不应在 sdk/esp-idf 下执行 git submodule update。

## 烧录与串口

确认硬件、电源及实际串口后自行执行：

```bash
bash sdk/tools/build.sh -p /dev/ttyUSB0 flash monitor
```

```powershell
.\sdk\tools\build.ps1 -Action flash -Port COM5
.\sdk\tools\build.ps1 -Action monitor -Port COM5
```

Ctrl+] 退出监视。默认 4MB Flash、3MB factory、DIO/40MHz，无 OTA。
本次重构不自动烧录或擦除设备；NVS 异常仍报错终止，不自动清除用户数据。
根目录 firmware 保留重构前交付物；本次构建的最新文件位于对应 build 目录，以 docs/VALIDATION.txt 为准。

## VS Code 一键编译与烧录

VS Code 打开 sdk 目录；以下命令行示例从仓库根目录执行。首次运行对应平台的 setup 脚本。WSL 通过 VS Code WSL 扩展打开目录。
Ctrl+Shift+B 默认运行 build + flash：Linux/WSL 调用 bash sdk/tools/build.sh build flash，
Windows 调用 powershell.exe -NoProfile -ExecutionPolicy Bypass -File sdk\tools\build.ps1 -Action build+flash。
显式先 build 再 flash，构建失败时不会执行烧录。编译成功后枚举串口；没有串口或指定的串口未连接时，
提示跳过烧录并返回成功，不影响普通编译。串口存在时仍由官方工具探测设备并下载；实际连接/烧录失败继续报错。
Windows/Linux 共用 sdk/tools/run_idf.py 中的这一判断，不需要额外 GUI 上位机。
单独执行 flash 仍保留官方失败行为；自动跳过只用于任务的 build + flash 组合。
需要仅编译时，通过“任务：运行任务”选择 build only。

默认由官方工具自动探测串口；有多个目标时可在启动 VS Code 的环境中设置 ESPPORT，重启 VS Code 后生效。
也可以直接执行指定串口的脚本命令：

```bash
bash sdk/tools/build.sh -p /dev/ttyUSB0 build flash
```

```powershell
.\sdk\tools\build.ps1 -Port COM5 -Action build+flash
```

Windows 需 USB 串口驱动；Linux 用户需串口访问权限；WSL2 需先把 USB 串口设备接入 WSL。
无自动下载电路的板卡仍需要手动配合 BOOT/EN，脚本无法代替物理接线。
默认不执行 erase-flash，不清空 NVS，不启动 monitor；只更新当前分区配置中的固件内容。

补全配置使用 Linux/Win32 两个自动选择的配置，分别读取 build/linux 或 build/windows 的 compile_commands.json。
首次使用先编译一次；如自定义构建输出目录，还需对应调整 compileCommands 路径。
settings.json 只调整搜索与文件监听，不改变编译参数，不关闭错误诊断。

无设备逻辑回归检查（激活 ESP-IDF 环境后执行）：`python sdk/tools/test_run_idf.py`。
